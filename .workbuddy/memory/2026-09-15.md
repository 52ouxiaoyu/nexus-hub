## pvz-web v3.11.0 —— 融合部件居中修复 + 投手补眉/投掷物校准/调价（已提交推送 a6084a0）

### 1) 核心根因：融合植物"被扔到右下角"
融合植物的第二部件用裸 `<img>`（`Plant.fusionOverlay`）叠加，它**不在 `.entity` 上**，
拿不到 CSS 里的 `transform: translate(-50%,-50%)` 居中基准；而代码又直接写
`this.fusionOverlay.style.transform = 'translate(x,y) scale(s)'` → 元素退化成"左上角对齐"，
整块部件相对宿主**偏右半宽 + 偏下半高**（贴图越大偏得越多）。

这就是用户说的「冰西瓜猫尾草 / 坚果射手 / 向日豌豆 / 毁灭向日葵…都把融合部件放到了
原植物的左下角或右下角」。

修法：给**全部 10 处** `fusionOverlay.style.transform` 前置 `translate(-50%, -50%) `。

**连带教训（重要）**：这批 `overTransform` 数值原本是在**错误的（左上角对齐）坐标系**里
试出来的，所以恢复中心对齐后必须**重新标定**，不能只改 CSS 语义：
- 地刺坚果 `translate(0,40px)` → `(0,24px)`：原值会让刺浮在坚果下方露 23px 缝
- 钢刺高坚果 `translate(0,40px)` → `(0,30px)`
- 大嘴坚果 `translate(0,-25px)` → `translate(20px,-25px)`：大嘴花立绘在 130×114
  画布里整体偏左 ~20px（**原图集如此**），直接居中会让头探出坚果左边 24px。
  补正后部件重合度 52% → 87%、部件↔宿主中心距 21.7px → 1.9px

## 方法论沉淀：**无法读图时如何验证视觉**（本轮最大收获）
本模型读不了图片（多次收到 "current model does not support images"），
所以视觉验证全部靠**数值化 + 字符画**，三件套：

1. **canvas 读像素求有效包围盒**（`/tmp/pvz_alphabox.js`）
   `drawImage` 后遍历 alpha>16，得到每个素材"在自身画布内的内容包围盒"，
   以及它相对画布中心的偏移（`relToCenter`）。GIF 画布常有大片透明留白，
   **只靠 naturalWidth 会算错落点**。
2. **PIL 按 CSS 变换数学复现合成**（`/tmp/fusion_layers.py`）
   CSS `transform: translate(-50%,-50%) translate(ox,oy) scale(s)` 且
   `transform-origin:center center` 时，**元素自身中心恰好落在 anchor+(ox,oy)**，
   并以自身中心缩放 s；`clip-path` 的百分比按**未变换**的元素盒算（先裁后缩放）。
   把这两条写成 PIL 合成 → 立刻能算出"部件覆盖宿主百分之几 / 两者中心距多少"。
3. **图层占位图 + 字符画**（`/tmp/fusion_layers.py` 的 `draw()`）
   逐像素标 `B`(只有宿主) / `O`(只有部件) / `X`(重叠) / 空格(都透明) ——
   **这比按亮度分类的字符画有用得多**，几何关系一眼可读。
   高分辨率亮度字符画（`/tmp/ascii_view.py`）用来认形状（如"火焰在上半、树桩在下半"）。

配套教训：
- 差分截图要**逐株隔离**（一次只种一株 + 与空场差分）。一次种一排时裁剪窗口会
  混入邻格像素，量出来的宽度恒等于裁剪窗宽。
- 断言脚本里算叠加件位置时**别忘了减画布中心**：
  正确式子是 `over.x0 = ox + (bbox.x0 - canvasCx) * s`。
